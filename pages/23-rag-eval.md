## 23. 검색 품질 평가

지금까지 청킹, 하이브리드 검색, 리랭킹을 다뤘다. 그런데 "검색 품질이 좋아졌다"는 것을 어떻게 아는가. 감으로 판단하면 개선인지 악화인지 알 수 없고, 어떤 기법을 붙여야 할지도 정할 수 없다. 이 장에서는 검색 품질을 수치로 측정하는 방법을 다룬다. 평가는 선택이 아니라 파이프라인 운영의 전제 조건이다.

### 무엇을 측정하는가: 검색과 생성의 분리

RAG 시스템의 최종 답변 품질은 두 단계의 합성 결과다. 검색 단계가 관련 문서를 잘 가져왔는지, 생성 단계가 가져온 문서를 바탕으로 정확한 답변을 만들었는지를 분리해서 측정해야 한다. 답변이 틀렸을 때 원인이 검색인지 생성인지 알아야 고칠 곳을 찾기 때문이다. 관련 문서를 못 가져왔는데 프롬프트를 고쳐 봐야 소용없고, 문서는 잘 가져왔는데 모델이 엉뚱하게 요약한다면 검색을 손댈 필요가 없다.

검색 평가는 질문과 정답 문서 집합이 필요하다. 각 테스트 질문마다 "이 질문에 답하려면 어떤 문서가 필요한가"를 미리 정해 둔다. 이를 골든 문서(golden documents)라고 한다. 생성 평가는 질문과 모범 답안이 필요하다.

### RAGAS 지표

RAGAS는 RAG 평가용으로 널리 쓰이는 프레임워크다. 대표적인 지표 네 가지를 이해하면 충분하다.

Faithfulness(충실도)는 생성된 답변이 검색된 컨텍스트에 근거하고 있는지를 측정한다. 답변의 각 주장을 컨텍스트에서 뒷받침할 수 있는지 확인한다. 이 값이 낮으면 모델이 컨텍스트를 무시하고 자체 지식으로 지어내고 있다는 뜻으로, 환각의 직접적인 신호다.

Answer relevancy(답변 관련성)는 답변이 질문에 실제로 답하고 있는지를 측정한다. 답변에서 역으로 질문을 생성해 보고 원래 질문과 얼마나 가까운지 비교하는 방식으로 계산한다. 답변이 장황하게 옆길로 새는 경우 이 값이 떨어진다.

Context precision(컨텍스트 정밀도)은 검색된 문서 중 관련 문서가 상위에 얼마나 잘 배치되었는지를 측정한다. 관련 없는 문서가 상위에 섞여 있으면 값이 낮아진다. 리랭킹의 효과를 직접 보여주는 지표다.

Context recall(컨텍스트 재현율)은 필요한 문서(골든 문서) 중 실제로 검색된 비율이다. 이 값이 낮으면 청킹이나 하이브리드 검색 쪽에 문제가 있다는 신호다. 리랭킹을 붙여도 개선되지 않는다.

### recall@k와 실무 측정

RAGAS 전체를 돌리기 부담스러울 때는 recall@k부터 시작하는 것이 좋다. recall@k는 상위 k개 검색 결과 안에 골든 문서가 얼마나 들어 있는지를 재는 단순한 지표다. recall@5가 0.9라면, 테스트 질문의 90퍼센트에서 상위 5개 안에 필요한 문서가 포함되었다는 뜻이다. 구현이 간단하고 해석이 명확해 파이프라인 변경 전후 비교용으로 적합하다. k는 실제 LLM에 전달하는 문서 수와 맞추는 것이 좋다. top-5를 전달한다면 recall@5를 본다.

### 테스트셋 만들기

평가의 품질은 테스트셋의 품질이 정한다. 좋은 테스트셋의 조건은 세 가지다. 첫째, 실제 사용자 질문 분포를 반영한다. 개발자가 만든 예쁜 질문이 아니라 로그에서 뽑은 실제 질문이어야 한다. 둘째, 난이도가 다양하다. 단일 문서로 답할 수 있는 쉬운 질문, 여러 문서를 조합해야 하는 어려운 질문, 답이 없는 질문(거절 테스트용)을 섞는다. 셋째, 정답을 미리 정한다. 각 질문마다 골든 문서와 모범 답안을 사람이 검증해 둔다.

테스트셋은 처음부터 크게 만들 필요가 없다. 50개에서 100개의 잘 검증된 질문이면 파이프라인 변경의 효과를 판단하기에 충분하다. 중요한 것은 한 번 만들고 끝이 아니라, 서비스 중 실패 사례를 발견할 때마다 테스트셋에 추가하는 것이다. 실패 사례가 쌓이면 회귀 테스트 역할을 한다.

### 따라 하기: recall@k 측정과 RAGAS 실행

```python
# recall@k 측정 예제 (검색 함수 search는 (query -> 문서 ID 리스트)를 반환한다고 가정)
def recall_at_k(test_set, search, k=5):
    hits = 0
    for item in test_set:
        retrieved = search(item["query"])[:k]
        # 골든 문서 중 하나라도 상위 k 안에 있으면 성공
        if any(g in retrieved for g in item["golden_doc_ids"]):
            hits += 1
    return hits / len(test_set)

# 테스트셋 예시 (실제로는 CSV나 JSON 파일로 관리)
test_set = [
    {"query": "약정 중 해지 위약금은?", "golden_doc_ids": ["doc-014", "doc-015"]},
    {"query": "요금제 변경 방법 알려줘", "golden_doc_ids": ["doc-003"]},
]

# 파이프라인 변경 전후 비교에 사용
# print("recall@5:", recall_at_k(test_set, search_v1, k=5))
```

```python
# RAGAS 실행 예제
# pip install ragas datasets
from datasets import Dataset
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall

# 평가 데이터: 질문, 검색된 컨텍스트, 생성된 답변, 모범 답안
data = {
    "question": ["약정 기간 중 해지하면 위약금이 얼마인가요?"],
    "contexts": [["약정 기간 내 해지 시 잔여 개월 수에 비례하여 위약금이 부과된다.",
                  "위약금은 최대 30만원을 초과하지 않는다."]],
    "answer": ["잔여 개월에 비례해 위약금이 부과되며, 최대 30만원을 넘지 않습니다."],
    "ground_truth": ["잔여 개월 수에 비례한 위약금이 부과되며 상한은 30만원이다."],
}
dataset = Dataset.from_dict(data)

result = evaluate(
    dataset,
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
)
print(result)
# faithfulness가 낮으면 생성 단계 점검, context_recall이 낮으면 검색 단계 점검
```

RAGAS 실행에는 LLM 호출이 필요하므로 비용이 든다. 매번 전체 지표보다는, 변경한 단계에 맞는 지표 위주로 돌리는 것이 경제적이다. 청킹을 바꿨다면 context_recall과 context_precision을, 프롬프트를 바꿨다면 faithfulness와 answer_relevancy를 본다.

### 지표별 병목 진단표

| 낮게 나온 지표 | 의미 | 먼저 볼 곳 |
|---|---|---|
| context_recall | 필요한 문서를 못 가져옴 | 청킹, 하이브리드 검색, 후보 수 |
| context_precision | 관련 없는 문서가 상위에 섞임 | 리랭킹, 점수 임계값 |
| faithfulness | 답변이 컨텍스트를 벗어남 | 프롬프트, 컨텍스트 길이, 모델 |
| answer_relevancy | 답변이 질문과 동떨어짐 | 프롬프트, 답변 길이 제한 |

이 표는 디버깅의 지도다. 답변이 틀렸을 때 네 지표 중 어디가 낮은지 보면 고칠 곳이 정해진다.

### 좋은 테스트 질문의 유형

테스트셋에는 다양한 유형의 질문을 섞는다.

- 단일 문서 질문: 하나의 문서로 답할 수 있다. 기본 검색 성능을 본다.
- 다중 문서 질문: 여러 문서를 조합해야 답할 수 있다. 검색 재현율과 생성의 종합 능력을 본다.
- 비교 질문: "A와 B 중 뭐가 더 저렴해?"처럼 두 대상을 대조한다. 여러 검색 결과를 종합하는 능력을 본다.
- 답이 없는 질문: 문서에 답이 없는 질문이다. "관련 정보를 찾지 못했습니다"처럼 정직하게 거절하는지를 본다. 이 유형이 없으면 모델이 없는 답을 지어내는 경향을 놓친다.
- 애매한 질문: "그거 얼마야?"처럼 맥락 없이는 답할 수 없는 질문이다. 추가 질문을 하거나 가정을 명시하는지를 본다.

각 유형을 10개에서 20개씩 준비하면 50개에서 100개의 균형 잡힌 테스트셋이 된다.

### 실패 사례를 테스트셋에 추가하는 흐름

서비스 운영 중 사용자가 "이 답변이 틀렸어요"라고 피드백하거나, 로그에서 이상한 답변을 발견하면 다음 순서로 처리한다.

```python
# 실패 사례를 테스트셋에 추가하는 기록 형식 (JSON 예시)
failure_case = {
    "query": "위약금 없이 해지하는 방법 알려줘",
    "expected_doc_ids": ["doc-021"],       # 답에 필요했던 문서
    "expected_answer": "약정 만료 후 해지하면 위약금이 없습니다.",
    "actual_answer": "위약금은 최대 30만원입니다.",  # 실제 잘못된 답변
    "failure_type": "검색 누락",            # 검색 누락 / 생성 오류 / 거절 실패
    "date_added": "2026-10-09",
}
# failure_type이 "검색 누락"이면 청킹과 검색을, "생성 오류"이면 프롬프트를 점검한다
print(failure_case["query"], "->", failure_case["failure_type"])
```

이렇게 쌓인 실패 사례는 회귀 테스트가 된다. 파이프라인을 바꿀 때마다 전체 테스트셋을 돌려, 기존에 고쳤던 문제가 다시 생기지 않았는지 확인한다. 테스트셋이 살아 있는 문서가 되는 것이다.

### 휴먼 평가를 병행하는 이유

자동 지표가 전부는 아니다. RAGAS도 결국 LLM으로 평가하므로, 평가 모델의 편향이 들어갈 수 있다. 중요한 변경(프롬프트 전면 개편, 모델 교체) 앞에서는 사람이 직접 답변을 읽어보는 휴먼 평가를 병행한다. 방법은 간단하다. 테스트셋에서 20개를 무작위로 뽑아 답변이 정확한지, 근거가 명확한지, 말투가 적절한지를 사람이 점수화한다. 자동 지표와 휴먼 평가가 같은 방향을 가리키면 변경을 확신할 수 있다. 방향이 다르면 자동 지표의 맹점을 의심해야 한다.

### 평가를 CI에 넣기

테스트셋이 갖춰지면 평가를 자동화한다. 파이프라인 코드를 바꿀 때마다 테스트셋을 돌려 지표가 떨어지지 않았는지 확인하는 것이다. 거창한 시스템이 필요 없다. 다음 같은 스크립트 하나로 시작할 수 있다.

```python
# evaluate_pipeline.py: 파이프라인 변경 전후를 비교하는 간단한 스크립트
import json

def load_test_set(path="test_set.json"):
    with open(path, encoding="utf-8") as f:
        return json.load(f)

def run_evaluation(search_fn, test_set, k=5):
    recalls, precisions = [], []
    for item in test_set:
        retrieved = search_fn(item["query"])[:k]
        golden = set(item["golden_doc_ids"])
        hit = len(golden & set(retrieved))
        recalls.append(hit / len(golden))            # 재현율
        precisions.append(hit / k)                   # 정밀도
    return sum(recalls) / len(recalls), sum(precisions) / len(precisions)

# 사용법: git 브랜치마다 결과를 기록하고 비교한다
# main 브랜치: recall=0.82, precision=0.61
# chunking 변경 브랜치: recall=0.87, precision=0.63 -> 개선 확인 후 병합
```

기준선을 파일에 기록해 두면 나중에 "예전보다 나빠졌다"는 것을 바로 알 수 있다. RAGAS 전체 지표를 매번 돌리기 부담스럽다면 recall@k와 precision@k만 CI에서 돌리고, RAGAS는 주 단위로 돌리는 식으로 빈도를 나눈다.

### 평가할 때 피해야 할 함정

첫째, 테스트셋에 과적합되는 것이다. 테스트 질문에만 잘 나오도록 파이프라인을 튜닝하면 실제 사용자 질문에서는 성능이 떨어진다. 테스트셋을 주기적으로 새 질문으로 교체하고, 가능하면 테스트셋을 비공개로 유지한다.

둘째, 지표 하나만 보는 것이다. recall@k만 올리려고 후보를 무작정 늘리면 정밀도가 떨어지고 LLM 컨텍스트가 오염된다. 재현율과 정밀도를 함께 보고, 최종적으로는 답변 품질까지 확인한다.

셋째, 평가 없이 변경을 배포하는 것이다. "별거 아닌 수정"이라도 검색 파이프라인에 닿았다면 평가를 돌린다. 토크나이저 하나를 바꿨을 뿐인데 BM25 점수가 통째로 바뀌는 일이 실제로 일어난다.

### 핵심 정리

- 검색과 생성을 분리해서 측정해야 무엇이 문제인지 알 수 있다. 답변 오류의 원인을 먼저 가른다.
- RAGAS의 네 지표는 각각 다른 병목을 가리킨다. faithfulness는 환각, context_recall은 검색 누락, context_precision은 순위 품질 문제다.
- recall@k는 간단하면서도 강력한 출발점이다. 파이프라인 변경 전후 비교에 바로 쓸 수 있다.
- 테스트셋은 실제 질문 50~100개로 시작하고, 실패 사례를 발견할 때마다 추가해 회귀 테스트로 키운다.
