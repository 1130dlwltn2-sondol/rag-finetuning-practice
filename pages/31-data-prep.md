## 31. 데이터 준비와 전처리

파인튜닝에서 모델의 성능을 좌우하는 가장 큰 요인은 학습 방법이 아니라 데이터이다. 같은 모델, 같은 설정으로 학습해도 데이터 품질에 따라 결과는 완전히 달라진다. 실무에서 파인튜닝이 실패하는 원인의 대부분은 하이퍼파라미터가 아니라 부실한 데이터에서 나온다. 이 장에서는 좋은 학습 데이터를 만드는 방법을 다룬다.

### 인스트럭션 데이터의 형식

파인튜닝용 데이터는 대부분 인스트럭션(instruction) 형식으로 만든다. 지시와 그에 대한 모범 답을 쌍으로 구성하는 방식이다. 크게 두 가지 형식이 널리 쓰인다.

첫째는 instruction, input, output 세 필드 형식이다. Alpaca 데이터셋에서 유래한 방식으로, 지시(instruction)와 추가 입력(input), 기대 출력(output)을 분리한다.

```json
{
  "instruction": "다음 고객 문의를 정중한 사과의 말로 시작하는 답변으로 바꿔 쓰세요.",
  "input": "배송이 왜 이렇게 늦어요?",
  "output": "배송이 지연되어 불편을 드린 점 진심으로 사과드립니다. ..."
}
```

둘째는 messages 형식이다. OpenAI의 대화 형식을 따르며, role이 system, user, assistant인 메시지들의 배열로 구성한다. 여러 턴의 대화를 그대로 표현할 수 있어 최근에는 이 형식이 더 많이 쓰인다.

```json
{
  "messages": [
    {"role": "system", "content": "당신은 친절한 고객 상담 직원입니다."},
    {"role": "user", "content": "배송이 왜 이렇게 늦어요?"},
    {"role": "assistant", "content": "배송이 지연되어 불편을 드린 점 진심으로 사과드립니다. ..."}
  ]
}
```

어떤 형식을 쓰든 중요한 것은 일관성이다. 학습 데이터 전체에서 형식을 통일해야 모델이 안정적으로 패턴을 배운다. 학습에 사용하는 라이브러리(TRL의 SFTTrainer 등)가 기대하는 형식에 맞추는 것도 잊지 말자.

### 양보다 품질

파인튜닝 데이터에서 양보다 품질이 중요하다는 것은 여러 연구에서 반복 확인된 사실이다. 수만 개의 잡다한 예제보다, 잘 선별된 수백 개의 고품질 예제가 더 좋은 결과를 낸다. LIMA라는 연구에서는 1,000개의 정성스럽게 만든 예제만으로 강력한 인스트럭션 튜닝이 가능함을 보였다.

고품질 데이터의 조건은 다음과 같다.

- 정답이 실제로 정확하다. 틀린 답을 학습시키면 모델이 틀린 패턴을 그대로 배운다.
- 지시가 명확하고 모호하지 않다. 애매한 지시는 모델에게 혼란을 준다.
- 답변이 원하는 형식과 톤을 정확히 보여 준다. 모델은 데이터의 스타일을 그대로 따라 한다.
- 중복이 적다. 같은 패턴의 반복은 학습 효율을 떨어뜨린다.

데이터를 만들 때는 "이 예제를 모델이 그대로 외워서 따라 해도 되는가"라는 기준으로 검수한다. 부끄러운 예제가 하나라도 있으면 학습 전에 고치거나 빼야 한다.

### 다양성과 오염 방지

데이터가 한 가지 유형에 치우치면 모델도 그 유형에만 잘 반응하게 된다. 예를 들어 짧은 질문만 모아 학습시키면 긴 문맥의 질문에는 제대로 답하지 못한다. 의도한 사용 범위를 커버하도록 질문 길이, 주제, 난이도, 형식을 고르게 분포시키는 것이 중요하다.

오염(contamination) 방지도 필수이다. 평가용으로 쓸 질문이나 그와 거의 같은 예제가 학습 데이터에 섞이면, 평가는 좋아 보이지만 실제 성능은 그렇지 않은 착시가 생긴다. 학습 데이터와 평가 데이터는 처음부터 완전히 분리해서 관리한다.

실무적인 분리 방법은 간단하다. 평가용 질문 집합을 먼저 만들고 별도 파일로 보관한 뒤, 학습 데이터 수집 과정에서 평가 질문과 유사도가 높은 예제는 제거한다. 간단한 문자열 유사도 검사만으로도 대부분의 오염을 막을 수 있다.

### 검증셋 분리

학습 데이터의 일부는 검증용(validation)으로 떼어 둔다. 보통 전체의 5~10%를 분리한다. 검증셋은 학습 중에 모델이 과적합되는지 확인하는 용도로 쓴다. 학습 데이터로만 평가하면 모델이 외운 것인지 이해한 것인지 구분할 수 없기 때문이다.

검증셋은 학습에 절대 사용하지 않는다. 파일 수준에서 분리하고, 학습 스크립트에서는 학습용 파일과 검증용 파일을 따로 지정한다. 33장에서 학습 코드를 다룰 때 이 분리가 실제로 어떻게 적용되는지 확인할 수 있다.

### 데이터 수집의 실무적인 방법

처음부터 빈손으로 데이터를 만드는 경우는 드물다. 실무에서 쓰는 수집 방법을 소개한다.

기존 상담 기록이나 문서가 있다면 가장 좋은 출발점이다. 실제 사용자의 질문과 직원의 모범 답변을 정제하면 현실감 있는 데이터가 된다. 개인정보는 반드시 제거하고, 특정 고객을 식별할 수 있는 내용은 각색한다.

기록이 없다면 강한 모델로 초안을 만든다. 목표 스타일을 설명하는 프롬프트와 몇 개의 예시를 주고 대량으로 생성한 뒤, 사람이 검수하면서 고른다. 이때 생성에 쓴 모델의 답변을 그대로 쓰지 말고, 도메인 지식이 맞는지는 반드시 사람이 확인한다.

공개 데이터셋을 활용하는 방법도 있다. Hugging Face Hub에는 다양한 인스트럭션 데이터셋이 올라와 있다. 라이선스를 확인하고, 필요한 부분만 가져와 자신의 형식에 맞게 변환한다. 공개 데이터셋은 범용성이 높지만 내 도메인과 정확히 맞지는 않으므로, 그대로 쓰기보다 섞어서 쓰는 편이 좋다.

### 합성 데이터의 함정

모델이 만든 데이터로 다른 모델을 학습시키는 합성 데이터 방식은 편리하지만 함정이 있다. 생성 모델의 편향과 오류가 그대로 전파된다. 예를 들어 생성 모델이 특정 표현을 과도하게 쓰면, 학습된 모델도 그 표현만 반복하게 된다.

이를 완화하려면 생성에 쓰는 프롬프트에 다양성을 강제한다. 질문 유형, 길이, 난이도를 지정하고, 여러 번에 나눠 생성한다. 그리고 사람이 표본을 검수해 품질이 무너지는 지점을 찾는다. 합성 데이터 100%보다는 사람 검수 데이터와 섞는 것을 권장한다.

### 라이선스와 저작권 주의

데이터의 출처가 명확해야 한다. 웹에서 긁어온 텍스트, 저작권이 있는 책이나 기사를 학습 데이터로 쓰면 법적 문제가 될 수 있다. 상용 서비스라면 법무 검토를 거치는 것이 안전하다.

공개 데이터셋도 라이선스가 제각각이다. 연구용으로만 허용된 데이터셋을 상용 모델 학습에 쓰면 안 된다. 데이터셋 카드를 읽고 라이선스를 확인하는 습관을 들이자. 자신이 만든 데이터라면 출처와 제작 과정을 기록해 두면 나중에 감사(audit) 대응에 도움이 된다.

### 따라 하기: 데이터 검수와 형식 변환

아래 코드는 messages 형식 데이터를 읽어 기본적인 품질 검사를 수행하고, TRL 학습에 바로 쓸 수 있는 형태로 저장하는 예제이다.

```python
# prepare_data.py — 학습 데이터 검수와 전처리
import json
from collections import Counter

INPUT_PATH = "raw_data.jsonl"      # {"messages": [...]} 형식
TRAIN_PATH = "train.jsonl"
VALID_PATH = "valid.jsonl"
VALID_RATIO = 0.1

def check_example(ex):
    # 형식 검사: 각 예제가 갖춰야 할 최소 조건
    msgs = ex.get("messages", [])
    if len(msgs) < 2:
        return False, "메시지가 2개 미만"
    roles = [m.get("role") for m in msgs]
    if "user" not in roles or "assistant" not in roles:
        return False, "user/assistant 역할 누락"
    for m in msgs:
        if not m.get("content", "").strip():
            return False, "빈 content 존재"
    last_assistant = [m for m in msgs if m["role"] == "assistant"][-1]
    if len(last_assistant["content"]) < 10:
        return False, "assistant 답변이 너무 짧음"
    return True, ""

examples = []
problems = Counter()
with open(INPUT_PATH, encoding="utf-8") as f:
    for i, line in enumerate(f):
        ex = json.loads(line)
        ok, reason = check_example(ex)
        if ok:
            examples.append(ex)
        else:
            problems[reason] += 1
            print("제외", i, ":", reason)

print("통과:", len(examples), "제외:", sum(problems.values()))
print("제외 사유:", dict(problems))

# 중복 제거: user 질문 텍스트 기준
seen = set()
unique = []
for ex in examples:
    q = ex["messages"][1]["content"]
    if q not in seen:
        seen.add(q)
        unique.append(ex)
print("중복 제거 후:", len(unique))

# 학습/검증 분리 (순서를 섞지 않고 뒤에서 자르면 시간 순서 편향 가능 — 셔플 권장)
import random
random.seed(42)
random.shuffle(unique)
n_valid = max(1, int(len(unique) * VALID_RATIO))
valid = unique[:n_valid]
train = unique[n_valid:]

for path, data in [(TRAIN_PATH, train), (VALID_PATH, valid)]:
    with open(path, "w", encoding="utf-8") as f:
        for ex in data:
            f.write(json.dumps(ex, ensure_ascii=False) + "\n")
print("학습:", len(train), "검증:", len(valid))
```

이 스크립트를 실행하면 형식에 맞지 않는 예제, 빈 답변, 중복이 자동으로 걸러진다. 실제 프로젝트에서는 여기에 도메인별 검수(사실 확인, 톤 검사)를 사람이 추가하는 것이 좋다.

### 핵심 정리

- 파인튜닝의 성패는 학습 방법이 아니라 데이터 품질에서 갈리며, 잘 만든 소량의 데이터가 잡다한 대량 데이터보다 낫다.
- 인스트럭션 데이터는 instruction/input/output 형식이나 messages 형식으로 일관되게 구성한다.
- 질문 길이, 주제, 난이도의 다양성을 확보하고, 평가 데이터와의 오염을 방지한다.
- 전체 데이터의 5~10%는 검증셋으로 분리해 학습에만 쓰지 않고 과적합 확인에 활용한다.
