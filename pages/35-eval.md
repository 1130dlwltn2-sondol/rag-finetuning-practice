## 35. 평가와 검증

학습을 마쳤다고 끝이 아니다. 파인튜닝된 모델이 정말 좋아졌는지, 나빠진 부분은 없는지를 확인하는 평가가 남았다. 30장에서 준비한 베이스라인이 여기서 빛을 발한다. 이 장에서는 손실을 이용한 과적합 확인부터 held-out 테스트, 벤치마크 비교, 사람 평가까지 실무적인 평가 절차를 다룬다.

### train/eval loss로 과적합 확인

가장 먼저 볼 것은 학습 손실과 검증 손실의 추이이다. 33장의 check_loss.py로 뽑아낸 값을 그래프로 그려 보면 모델 상태를 한눈에 파악할 수 있다.

정상적인 학습에서는 두 손실이 함께 내려간다. 학습 손실만 내려가고 검증 손실이 어느 지점부터 올라가기 시작하면 과적합이다. 모델이 학습 데이터를 외우기 시작했다는 뜻이다. 반대로 두 손실이 모두 높은 채로 멈추면 학습 부족(underfitting)으로, 에폭을 늘리거나 학습률을 조정해 본다.

실무적인 판단 기준은 다음과 같다.

- 검증 손실이 최소가 되는 체크포인트를 최종 모델로 선택한다. 마지막 체크포인트가 항상 최선은 아니다.
- 검증 손실이 2~3 에폭 연속으로 오르면 학습을 중단하고 그 이전 체크포인트를 쓴다.
- 학습 손실과 검증 손실의 차이가 크면 데이터가 부족하거나 모델이 데이터를 외우고 있다는 신호이다.

손실은 참고 지표일 뿐 최종 판단 기준은 아니다. 손실이 좋아졌다고 실제 답변이 좋아졌다는 보장은 없으므로, 반드시 별도의 평가를 병행해야 한다.

### held-out 테스트

held-out 테스트는 학습에 전혀 쓰지 않은 별도의 테스트셋으로 모델을 평가하는 것이다. 31장에서 학습 데이터와 분리해 둔 평가용 질문 집합이 바로 이것이다. 베이스라인 측정 때 썼던 그 질문 집합으로 학습 후 모델을 다시 측정하고, 학습 전 점수와 비교한다.

평가 지표를 정할 때는 작업의 성격을 반영한다. 정답이 명확한 작업(분류, 추출)은 정확도나 F1 점수를 쓴다. 자유로운 생성 작업은 채점 기준(rubric)을 만들어 점수를 매긴다. 예를 들어 고객 응대라면 정확성, 정중함, 형식 준수를 각각 1~5점으로 채점하는 식이다.

채점은 사람이 직접 하거나 강한 모델을 심사자로 쓰는 LLM-as-judge 방식을 쓴다. LLM 심사는 빠르지만 편향이 있을 수 있어, 중요한 판단은 사람이 표본을 검수하는 것이 좋다. 어떤 방식을 쓰든 학습 전후에 같은 기준을 적용해야 비교가 의미 있다.

### 기준 벤치마크 비교

파인튜닝이 모델의 기존 능력을 해치지 않았는지도 확인해야 한다. 특정 작업에 맞추느라 일반적인 능력을 잃는 현상을 catastrophic forgetting이라고 한다. 이를 확인하기 위해 학습 전후에 공개 벤치마크 몇 개를 돌려 본다.

모든 벤치마크를 돌릴 필요는 없다. 작업과 관련 있는 영역에서 1~2개만 골라 추이를 본다. 예를 들어 한국어 고객 상담 모델이라면 한국어 이해 벤치마크의 점수가 학습 전과 비슷한 수준을 유지하는지 확인한다. 큰 하락이 보이면 학습률이나 에폭을 낮추거나, 일반 데이터를 일부 섞어 학습하는 방법을 고려한다.

벤치마크 실행에는 lm-evaluation-harness 같은 도구를 쓴다. 명령어 하나로 여러 벤치마크를 돌릴 수 있어 편리하다. 점수를 표로 정리해 학습 전후를 비교하면 퇴행 여부를 명확히 판단할 수 있다.

### 휴먼 평가

숫자로 잡히지 않는 품질은 사람이 직접 봐야 한다. 휴먼 평가는 평가자가 모델의 답변을 읽고 기준에 따라 점수를 매기는 방식이다. 비용이 들지만 가장 신뢰할 수 있는 평가이다.

휴먼 평가를 설계할 때 주의할 점은 다음과 같다.

- 평가자에게 명확한 채점 기준과 예시를 제공한다. 기준이 모호하면 평가자마다 점수가 달라진다.
- 학습 전후 모델의 답변을 섞어서 보여 주고, 어느 모델의 답변인지 숨긴다(blind 평가). 그래야 공정하다.
- 한 질문에 여러 평가자가 참여하면 점수의 신뢰도가 올라간다.
- 정량 지표와 함께 "이 답변이 실제로 도움이 되는가" 같은 정성적 의견도 수집한다.

소규모 프로젝트에서는 팀원 2~3명이 50개 질문씩만 평가해도 충분한 신호를 얻을 수 있다. 빈틈없는 평가 설계를 기다리느라 평가 자체를 미루는 것보다, 간단하게라도 실행하는 편이 낫다.

### LLM-as-judge 실습

강한 모델을 심사자로 쓰는 LLM-as-judge는 빠르고 저렴한 평가 방법이다. 아래는 두 답변을 비교해 더 나은 쪽을 고르는 심사 프롬프트 예제이다.

```python
# llm_judge.py — 두 모델 답변을 비교하는 심사 프롬프트
JUDGE_PROMPT = """다음은 같은 질문에 대한 두 개의 답변입니다.
정확성, 도움이 되는 정도, 지시 준수 여부를 기준으로 더 나은 답변을 고르세요.
답변 A와 답변 B의 순서는 무작위이므로 순서에 휘둘리지 마세요.
결과는 반드시 다음 형식 중 하나로만 출력하세요: A가 더 낫다 / B가 더 낫다 / 비슷하다

질문: {question}

답변 A:
{answer_a}

답변 B:
{answer_b}
"""

def judge(question, answer_a, answer_b, judge_model):
    prompt = JUDGE_PROMPT.format(
        question=question, answer_a=answer_a, answer_b=answer_b
    )
    return judge_model.generate(prompt).strip()
```

LLM 심사의 편향을 줄이는 요령이 있다. 답변 순서를 바꿔 두 번 심사하고 결과가 일치할 때만 인정한다. 심사 모델이 자기와 비슷한 스타일을 선호하는 경향이 있으므로, 중요한 결정은 사람 검수와 병행한다. 심사 기준을 프롬프트에 구체적으로 적을수록 일관성이 올라간다.

### 회귀 테스트 자동화

한 번 만든 평가를 계속 재사용하면 회귀 테스트가 된다. 모델을 업데이트할 때마다 같은 질문 집합으로 평가를 돌리고 점수를 기록한다. 점수가 떨어진 영역이 보이면 어떤 변경이 원인인지 추적할 수 있다.

간단한 회귀 테스트는 스크립트 하나로 충분하다. 평가 질문 파일, 채점 함수, 결과 저장 형식을 고정하고, 모델 버전별로 결과를 CSV에 쌓는다. 버전이 늘어날수록 추이가 보여 어떤 업데이트가 도움이 되었는지 판단할 수 있다.

CI에 연결하면 더 좋다. 어댑터 파일이 새로 생길 때마다 자동으로 평가를 돌리고, 기준 점수보다 떨어지면 배포를 막는 식이다. 소규모 팀에서는 수동 실행만으로도 충분한 효과를 본다.

### 평가 결과를 기록하는 습관

평가를 돌릴 때마다 설정과 결과를 함께 기록한다. 모델 버전, 학습 데이터 버전, 하이퍼파라미터, 평가 점수를 한 파일에 남긴다. 나중에 "그때 그 설정이 뭐였지"라는 상황을 막아준다.

간단한 실험 기록 형식은 다음과 같다.

```
실험: sft-v3
베이스: gemma-2-9b-it
데이터: train.jsonl (3,000개, 2026-10-08 검수본)
설정: r=16, lr=2e-4, epoch=3, batch=16
검증 손실: 1.42 (epoch 2 체크포인트 선택)
held-out 정확도: 0.81 (베이스라인 0.62)
벤치마크: 한국어 이해 0.74 (학습 전 0.75, 유지)
```

이런 기록이 쌓이면 어떤 시도가 효과가 있었는지 한눈에 보인다. 파인튜닝은 반복 실험의 연속이므로, 기록이 곧 자산이다.

### 따라 하기: 학습 전후 비교 리포트

30장의 baseline_answers.jsonl과 학습 후 답변 파일을 비교하는 스크립트이다. 간단한 채점 함수를 붙이면 정량 비교가 된다.

```python
# compare_eval.py — 학습 전후 답변 비교 리포트
import json

BEFORE_PATH = "baseline_answers.jsonl"   # 학습 전 답변
AFTER_PATH = "finetuned_answers.jsonl"   # 학습 후 답변 (같은 질문 집합)

def load_answers(path):
    data = {}
    with open(path, encoding="utf-8") as f:
        for line in f:
            row = json.loads(line)
            data[row["question"]] = row["answer"]
    return data

before = load_answers(BEFORE_PATH)
after = load_answers(AFTER_PATH)

print("질문 수:", len(before), "/", len(after))
print("공통 질문 수:", len(set(before) & set(after)))
print()

# 길이 분포 같은 간단한 휴리스틱 비교 (실제로는 작업별 채점 함수 사용)
def avg_len(d):
    vals = list(d.values())
    return sum(len(v) for v in vals) / max(len(vals), 1)

print("학습 전 평균 답변 길이:", round(avg_len(before)))
print("학습 후 평균 답변 길이:", round(avg_len(after)))
print()

# 나란히 비교 출력 (사람 검수용)
for i, q in enumerate(list(before)[:5]):
    print("=" * 60)
    print("질문:", q)
    print("-" * 60)
    print("[학습 전]", before[q][:300])
    print("-" * 60)
    print("[학습 후]", after.get(q, "(없음)")[:300])
print("=" * 60)
```

실제 프로젝트에서는 avg_len 같은 휴리스틱 대신 작업에 맞는 채점 함수를 넣어 점수를 계산한다. 나란히 비교 출력은 휴먼 평가 때 평가자에게 보여 줄 자료로 활용할 수 있다.

### 핵심 정리

- 학습 손실과 검증 손실의 추이로 과적합을 확인하고, 검증 손실이 최소인 체크포인트를 선택한다.
- 손실은 참고 지표일 뿐이며, 학습에 쓰지 않은 held-out 테스트셋으로 학습 전후를 같은 기준으로 비교해야 한다.
- 공개 벤치마크로 기존 능력의 퇴행이 없는지 확인한다.
- 숫자로 잡히지 않는 품질은 blind 방식의 휴먼 평가로 확인하며, 간단하게라도 실행하는 것이 중요하다.
