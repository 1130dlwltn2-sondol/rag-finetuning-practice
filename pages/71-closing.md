## 71. 마무리

이 책은 RAG와 LLM 파인튜닝이라는 두 개의 큰 기술을 한 권에 담았다. Part 1에서 RAG의 기본 파이프라인을 만들었고, Part 2에서 검색 품질을 끌어올리는 방법을 배웠다. Part 3에서는 파인튜닝의 데이터 준비부터 학습, 정렬, 배포까지 따라갔다. Part 4에서는 두 기술을 언제 쓰고 어떻게 함께 쓰는지를 정리하고, 사내 문서 Q&A 챗봇이라는 실전 프로젝트로 묶었다.

### 전체 요약: 책 한 권을 다섯 문단으로

첫째, RAG는 모델 바깥에 지식을 두는 기술이다. 문서를 청킹하고 임베딩해 벡터 데이터베이스에 저장한 뒤, 질문이 들어오면 관련 문서를 찾아 프롬프트에 붙여준다. 지식 마감과 환각이라는 LLM의 한계를 문서라는 근거로 보완한다. 지식이 자주 바뀌거나 출처를 보여줘야 할 때 가장 먼저 고려할 방법이다.

둘째, 검색 품질은 RAG의 성패를 가른다. 청킹은 400~512 토큰에 오버랩 10~20퍼센트를 기준으로 잡고, 키워드 검색이 필요한 환경에서는 BM25와 벡터를 병렬로 돌려 RRF로 융합하는 하이브리드 검색을 쓴다. 정밀도가 병목으로 측정될 때만 리랭킹을 추가한다. 평가는 RAGAS의 faithfulness와 answer relevancy, recall@k로 검색과 생성을 분리해서 측정한다.

셋째, 파인튜닝은 최후의 수단이다. 프롬프트 개선, RAG, 퓨샷 예제로 해결되지 않을 때 검토한다. 시작 전에는 평가 베이스라인을 만들고, 데이터는 양보다 품질을 우선한다. LoRA와 QLoRA 덕분에 16GB GPU 한 장으로도 큰 모델을 학습할 수 있게 되었고, SFT 이후에는 DPO로 선호도를 정렬한다. train loss와 eval loss를 함께 보며 과적합을 확인하고, 배포는 어댑터 병합과 분리 서빙 중 상황에 맞게 고른다.

넷째, 선택의 기준은 명확하다. 근거 제시가 필요하거나 지식이 자주 바뀌면 RAG를, 말투와 형식을 모델에 익히고 싶으면 파인튜닝을 고른다. 실무에서는 둘을 함께 쓰는 경우가 많다. 지식과 근거는 RAG가, 말투와 형식은 파인튜닝이 담당하는 분업이 유지 비용 면에서 합리적이다.

다섯째, 프로젝트는 질문부터 시작한다. 사내 문서 Q&A 챗봇 프로젝트에서 본 것처럼, 질문 목록이 평가셋이 되고 평가셋이 개선의 기준이 된다. 최소 동작 파이프라인을 먼저 만들고, 평가로 병목을 확인한 뒤 하이브리드 검색, 리랭킹, 파인튜닝을 순서대로 붙인다.

### 핵심 한 문장

지식은 문서에 맡기고(RAG), 행동은 모델에 가르치고(파인튜닝), 선택은 측정으로 한다.

### 책을 덮기 전, 다음 단계 로드맵

이 책을 다 읽었다면 다음은 직접 만드는 순서다. 아래 로드맵은 60장의 프로젝트를 개인 학습용으로 축소한 것이다.

1단계: 작은 문서 모음으로 RAG 파이프라인을 돌린다. 관심 있는 분야의 문서 20~50개를 모아 13장의 코드를 실행해본다. 처음에는 검색 결과가 기대와 다를 것이다. 그 차이가 배움이다.

2단계: 평가셋 20문항을 만든다. 스스로 질문을 쓰고 정답 근거 문서를 연결한다. recall@5를 재보고, 0.7 아래라면 청킹과 하이브리드 검색을 손본다.

3단계: 답변 품질을 눈으로 확인한다. 검색은 잘되는데 답이 이상하다면 프롬프트를 고치고, 그래도 말투와 형식이 마음에 들지 않는다면 그때 파인튜닝을 검토한다. 이 순서가 30장의 최후 수단 원칙이다.

4단계: 작은 파인튜닝을 한 번 돌려본다. 공개 인스트럭션 데이터셋으로 QLoRA 학습을 실행해보고, 학습 곡선(train loss와 eval loss)을 읽는 감각을 익힌다. 자신의 데이터가 아니어도 학습 파이프라인을 돌려보는 경험 자체가 값지다.

5단계: 두 기술을 붙여본다. 파인튜닝한 모델 위에 RAG를 얹고, 검색된 문서와 모델 지식이 충돌할 때 어떻게 동작하는지 관찰한다. 프롬프트에 우선순위를 명시하는 실험을 해본다.

각 단계에서 막히면 공식 문서로 돌아간다. 아래 목록은 이 책에서 다룬 핵심 도구들의 공식 문서다.

### 이 책을 스터디 교재로 쓰는 방법

혼자 읽는 것도 좋지만, 스터디로 함께 읽으면 이해가 깊어진다. 4주 구성을 제안한다.

1주차: Part 1을 읽고 13장의 첫 RAG 시스템을 각자 돌려본다. 같은 문서로 검색해보고 서로 다른 질문을 던져본 뒤, 어떤 질문에서 검색이 실패하는지 공유한다.

2주차: Part 2를 읽고 1주차의 실패 사례를 개선한다. 청크 크기를 바꿔보고, 하이브리드 검색을 붙여보고, recall@5가 얼마나 오르는지 측정한다. 측정 결과를 공유하는 것이 스터디의 핵심이다.

3주차: Part 3을 읽고 작은 파인튜닝을 돌려본다. 공개 데이터셋으로 QLoRA 학습을 실행하고 학습 곡선을 함께 읽는다. 과적합이 일어나는 지점을 찾는 것이 목표다.

4주차: Part 4를 읽고 각자의 실무 아이디어에 40장의 선택 기준을 적용해본다. 서로의 선택에 질문을 던지고, 60장의 프로젝트 단계대로 기획서를 써본다.

스터디에서 가장 중요한 규칙은 하나다. "돌려보지 않고 의견만 내지 않는다." 코드는 실행해보고, 숫자는 재보고 이야기한다. 이 책이 강조한 측정 우선의 태도를 스터디에도 적용하는 것이다.

### 실무에서 기억할 세 가지 원칙

책을 덮고 현장으로 돌아갈 때, 아래 세 가지만큼은 기억해주길 바란다.

첫째, 측정 없는 개선은 없다. 검색이 문제인지 생성이 문제인지 재지 않고 리랭킹을 붙이거나 모델을 바꾸는 것은 운에 맡기는 것과 같다. recall@k, faithfulness 같은 지표를 먼저 재고, 병목이 확인된 곳에만 손을 댄다. 이 원칙 하나만 지켜도 대부분의 삽질을 피할 수 있다.

둘째, 단순한 것부터 시작한다. 처음부터 하이브리드 검색, 리랭킹, 에이전틱 루프를 다 붙인 시스템은 디버깅이 어렵다. 최소 동작 파이프라인을 먼저 만들고, 평가로 부족한 지점을 찾은 뒤 하나씩 추가한다. 복잡도는 필요할 때만 올린다.

셋째, 데이터가 모델보다 오래 간다. 모델은 버전이 바뀌고 API는 단종되지만, 잘 만든 평가셋과 문서 메타데이터는 계속 쓸 수 있다. 파인튜닝 데이터든 RAG 문서든, 데이터에 투자한 시간은 가장 오래 남는 자산이다. 프로젝트 초반에 데이터 정리에 시간을 쓰는 것을 아까워하지 말자.

이 세 가지는 RAG와 파인튜닝을 넘어 어떤 AI 프로젝트에도 통하는 태도다. 기술은 바뀌지만, 측정하고, 단순하게 시작하고, 데이터에 투자하는 습관은 바뀌지 않는다.

### 마지막으로: 지식을 어디에 둘 것인가

이 책의 첫 장에서 던진 질문을 다시 꺼낸다. LLM의 한계는 지식 마감과 환각이었다. RAG는 그 한계를 문서라는 외부 지식으로 메웠고, 파인튜닝은 모델 자체를 바꿔 메웠다. 두 기술은 결국 "지식을 어디에 둘 것인가"라는 하나의 질문에 대한 서로 다른 답이다.

문서에 두면 바꾸기 쉽고 근거를 보여주기 좋다. 모델에 넣으면 말투와 형식이 몸에 배고 호출이 가벼워진다. 어느 쪽이 우월한가가 아니라, 자신의 문제에 어느 답이 맞는가가 중요하다. 그리고 대부분의 실무 문제는 두 답을 함께 요구한다.

이 질문에 답하는 힘은 이론이 아니라 경험에서 나온다. 문서를 모아 인덱싱해보고, 검색이 실패하는 모습을 보고, 평가 지표를 재보고, 파인튜닝 학습 곡선을 들여다보는 경험 말이다. 이 책의 코드 예제들은 그 경험을 시작하기 위한 발판이다. 발판 위에서 머물지 말고, 자신의 문서와 자신의 질문으로 직접 부딪혀보길 바란다.

기술은 계속 바뀔 것이다. 새로운 임베딩 모델이 나오고, 더 효율적인 학습 기법이 등장하고, 프레임워크의 API가 바뀔 것이다. 하지만 "측정하고, 단순하게 시작하고, 데이터에 투자하라"는 태도는 바뀌지 않는다. 이 책이 전하고자 한 것은 기술의 목록이 아니라 그 태도였다.

| 23. 검색 품질 평가 | 검색과 생성을 분리해서 재는 것이 원칙이다 |
| 24. 에이전틱 RAG | 에이전트가 검색 필요를 판단하고 검색-추론 루프를 돈다 |
| 30. 파인튜닝이란 무엇인가 | 최후의 수단, 프롬프트와 RAG로 안 될 때 검토한다 |
| 31. 데이터 준비와 전처리 | 품질이 양보다 중요하고 검증셋 분리는 필수다 |
| 32. LoRA와 QLoRA | 저랭크 행렬만 학습하고 4비트 양자화로 메모리를 아낀다 |
| 33. 학습 설정과 하이퍼파라미터 | 학습률, 에포크, 배치 크기를 이해하고 프레임워크를 고른다 |
| 34. DPO와 선호도 최적화 | chosen과 rejected 쌍으로 SFT 이후 정렬을 다듬는다 |
| 35. 평가와 검증 | train/eval loss로 과적합을 보고 held-out으로 검증한다 |
| 36. 추론 배포와 서빙 | 어댑터 병합과 분리 서빙 중 상황에 맞게 고른다 |
| 40. RAG와 파인튜닝 선택 | 근거와 변경 빈도는 RAG, 말투와 형식은 파인튜닝이 기본 |
| 60. 실전 프로젝트 | 질문부터 시작해 측정으로 병목을 찾고 단계별로 키운다 |
| 70. 확인 문제 | 틀린 파트로 돌아가는 것이 가장 빠른 복습이다 |

### 감사 인사

이 책을 끝까지 읽어주셔서 감사합니다. RAG와 파인튜닝은 따로 배우면 각각 유용한 기술이지만, 함께 놓고 보면 "지식을 어디에 둘 것인가"라는 하나의 질문으로 수렴합니다. 이 질문에 대한 답을 찾는 과정이 곧 실무에서의 의사결정입니다.

책을 읽는 데서 그치지 말고, 작은 문서 모음으로 RAG 파이프라인 하나를 직접 돌려보시길 바랍니다. 검색 결과가 기대와 다르게 나올 때, 그 차이가 다음 배움이 됩니다. 평가 지표를 재고, 병목을 찾고, 하나씩 개선해나가는 과정이 이 책이 말하고자 했던 전부입니다.

여러분의 프로젝트가 잘 동작하기를 바랍니다. 감사합니다.
