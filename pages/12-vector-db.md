## 12. 벡터 데이터베이스 선택과 구축

앞 장에서 문서를 벡터로 바꾸는 방법까지 배웠다. 이제 남은 문제는 저장과 검색이다. 문서가 수백만 건이 되면 모든 벡터와 하나씩 거리를 재는 방식으로는 응답 속도가 나오지 않는다. 벡터를 효율적으로 저장하고 빠르게 찾는 역할을 하는 것이 벡터 데이터베이스다.

### 벡터 데이터베이스의 개념

벡터 데이터베이스는 벡터와 원본 텍스트(메타데이터 포함)를 함께 저장하고, 질문 벡터와 가장 가까운 벡터들을 빠르게 찾아주는 전용 저장소다. 일반 관계형 데이터베이스가 "값이 정확히 일치하는 행 찾기"에 특화되어 있다면, 벡터 데이터베이스는 "벡터 공간에서 가장 가까운 이웃 찾기"에 특화되어 있다.

RAG 파이프라인에서 벡터 데이터베이스가 담당하는 구간은 인덱싱과 검색 두 단계다. 인덱싱 단계에서는 문서 조각마다 임베딩 벡터를 만들어 저장한다. 검색 단계에서는 질문을 벡터로 바꾼 뒤 데이터베이스에 "이 벡터와 가장 가까운 상위 k개"를 요청한다. 데이터베이스는 밀리초 단위로 결과를 돌려준다.

### ANN: 왜 근사 탐색인가

가장 정확한 방법은 모든 벡터와 거리를 재서 상위 k개를 뽑는 것이다. 이를 정확 최근접 이웃 탐색이라고 한다. 하지만 문서가 백만 건이고 벡터 차원이 1024라면, 질문 하나당 10억 번의 곱셈을 해야 한다. 정확하지만 너무 느리다.

대신 쓰는 방법이 근사 최근접 이웃(ANN, Approximate Nearest Neighbor) 탐색이다. 완벽히 정확한 답을 포기하고, 거의 정확한 답을 매우 빠르게 구하는 방식이다. 대표적인 알고리즘이 HNSW다. 벡터들을 여러 층의 그래프로 연결해 두고, 위층에서 대략적인 방향을 잡은 뒤 아래층으로 내려가며 점점 정밀하게 찾는 구조다. 산 정상에서 마을을 찾는다고 생각하면 된다. 먼저 산 위에서 마을이 있는 방향을 대략 잡고, 내려가면서 점점 정확히 찾는 방식이다.

ANN은 탐색할 후보 수를 조절할 수 있어서 속도와 정확도를 맞바꿀 수 있다. 후보를 많이 보면 정확해지고 느려지고, 적게 보면 빨라지고 조금 부정확해진다. 이 조절 파라미터는 나중에 실제 데이터로 성능을 측정하며 정하는 것이 좋다.

### 대표 벡터 데이터베이스 비교

| 제품 | 형태 | 특징 |
|---|---|---|
| Chroma | 오픈소스 라이브러리 | 설치가 간단하고 Python 친화적. 프로토타입과 소규모 서비스에 적합 |
| FAISS | 오픈소스 라이브러리 (Meta) | 속도가 빠르고 메모리 효율이 좋음. 서버 기능은 없어 직접 래핑 필요 |
| pgvector | PostgreSQL 확장 | 기존 PostgreSQL에 벡터 검색 추가. 관계형 데이터와 함께 쓰기 좋음 |
| Qdrant | 오픈소스 (서버) | 필터링과 페이로드 관리가 강함. Rust 기반으로 빠름 |
| Weaviate | 오픈소스 (서버) | 스키마 기반 관리와 하이브리드 검색 내장 |
| Milvus | 오픈소스 (서버) | 대규모 분산 환경에 강함. 수십억 벡터까지 확장 |
| Pinecone | 관리형 클라우드 | 서버 관리 불필요. 사용량 과금. 비용이 높은 편 |

선택 기준을 정리하면 다음과 같다. 먼저 규모다. 문서가 수만 건 이하인 프로토타입이라면 Chroma나 FAISS로 충분하다. 수백만 건 이상으로 커지면 Qdrant나 Milvus 같은 전용 서버를 검토한다. 다음은 운영 방식이다. 서버를 직접 운영할 인력이 없다면 Pinecone 같은 관리형을, 이미 PostgreSQL을 쓰고 있다면 pgvector를 쓰는 것이 현실적이다. 마지막은 필터링 요구다. "2024년 이후 문서만 검색" 같은 메타데이터 필터가 중요하면 Qdrant나 Weaviate가 편하다.

과도한 선택은 피하는 것이 좋다. 이 책의 실습과 소규모 서비스에서는 Chroma로 시작해서, 데이터가 커지거나 요구사항이 복잡해지면 그때 서버형으로 옮기는 순서를 권장한다.

### 따라 하기 실습: Chroma로 벡터 DB 구축하기

Chroma는 pip install chromadb 한 줄로 설치되는 가벼운 벡터 데이터베이스다. 내장 임베딩 모델을 쓰면 별도 임베딩 설정 없이 바로 실습할 수 있다.

```python
import chromadb

if __name__ == "__main__":
    # 클라이언트를 만들고 컬렉션(테이블 같은 개념)을 준비한다
    client = chromadb.Client()
    collection = client.create_collection(name="company_docs")

    docs = [
        "연차 휴가는 입사 1년 미만 직원도 월 1일씩 사용할 수 있다.",
        "연차 수당은 미사용 연차에 대해 통상임금의 100%를 지급한다.",
        "재택근무는 주 2일까지 가능하며 팀장 승인이 필요하다.",
        "회의실 예약은 사내 인트라넷에서 최대 2주 전까지 가능하다.",
    ]

    # 문서를 저장한다. id는 문서마다 고유해야 한다
    collection.add(
        documents=docs,
        ids=["doc1", "doc2", "doc3", "doc4"],
        metadatas=[
            {"category": "휴가", "year": 2026},
            {"category": "휴가", "year": 2026},
            {"category": "근무", "year": 2025},
            {"category": "시설", "year": 2025},
        ],
    )

    # 질문과 가장 가까운 문서 2개를 검색한다
    result = collection.query(
        query_texts=["6개월차 직원의 휴가는 어떻게 되나요?"],
        n_results=2,
    )

    for doc, meta, dist in zip(
        result["documents"][0], result["metadatas"][0], result["distances"][0]
    ):
        print(f"거리 {dist:.3f} | {meta} | {doc}")
```

Chroma는 저장할 때 자동으로 임베딩을 만들고, 검색할 때는 질문을 같은 모델로 임베딩해 거리를 잰다. 앞 장에서 배운 "같은 모델로 인덱싱과 질의를 해야 한다"는 원칙이 여기서 자동으로 지켜진다.

메타데이터 필터도 함께 써 보자. 아래처럼 where 조건을 추가하면 특정 분류의 문서 안에서만 검색한다.

```python
    filtered = collection.query(
        query_texts=["휴가 규정을 알려줘"],
        n_results=2,
        where={"category": "휴가"},
    )
    print(filtered["documents"][0])
```

데이터가 파일로 남아야 한다면 클라이언트 생성 시 저장 경로를 지정한다. chromadb.PersistentClient(path="./chroma_db") 처럼 쓰면 프로그램이 끝나도 데이터가 유지된다.

### ANN 알고리즘 조금 더 깊이

앞에서 HNSW를 산에 비유해 설명했다. 실무에서 자주 만나는 다른 ANN 방식도 간단히 알아두자.

IVF(역색인 파일)는 벡터들을 미리 여러 군집으로 나눠 두는 방식이다. 검색할 때는 질문과 가까운 군집 몇 개만 뒤진다. 도서관에서 책을 찾을 때 전체 서가를 뒤지지 않고 해당 분류의 서가만 보는 것과 같다. 군집 수를 늘리면 빨라지지만 정확도가 조금 떨어진다.

PQ(곱 양자화)는 벡터 자체를 압축하는 방식이다. 1024차원 벡터를 훨씬 작은 코드로 바꿔 메모리에 올린다. 메모리가 부족한 환경에서 대량의 벡터를 다룰 때 유용하다. 대신 압축 과정에서 약간의 정확도 손실이 생긴다. FAISS에서 자주 쓰이는 기법이다.

HNSW는 정확도가 높고 속도가 빠른 대신 메모리를 많이 쓴다. IVF는 메모리와 속도의 균형이 좋고, PQ는 메모리를 최우선으로 아낄 때 쓴다. 대부분의 벡터 DB는 이들을 조합해 제공하므로, 처음에는 기본 설정을 쓰고 데이터가 커지면 그때 조정하면 된다.

### 따라 하기 실습: FAISS로 가볍게 검색하기

FAISS는 서버 없이 라이브러리 형태로 쓰는 고속 검색 엔진이다. 임베딩은 sentence-transformers로 만들고, 검색만 FAISS에 맡기는 조합이 흔하다. pip install faiss-cpu sentence-transformers numpy를 설치한다.

```python
import faiss
import numpy as np
from sentence_transformers import SentenceTransformer

if __name__ == "__main__":
    model = SentenceTransformer("all-MiniLM-L6-v2")

    docs = [
        "연차 휴가는 입사 1년 미만 직원도 월 1일씩 사용할 수 있다.",
        "연차 수당은 미사용 연차에 대해 통상임금의 100%를 지급한다.",
        "재택근무는 주 2일까지 가능하며 팀장 승인이 필요하다.",
        "회의실 예약은 사내 인트라넷에서 최대 2주 전까지 가능하다.",
    ]

    # 문서를 임베딩하고 FAISS 인덱스에 넣는다
    doc_vecs = model.encode(docs).astype("float32")
    dimension = doc_vecs.shape[1]
    index = faiss.IndexFlatL2(dimension)  # 정확한 거리 계산 인덱스
    index.add(doc_vecs)

    # 질문을 검색한다
    query_vec = model.encode(["6개월차 직원의 휴가는 어떻게 되나요?"]).astype("float32")
    distances, indices = index.search(query_vec, k=2)

    for rank, (dist, idx) in enumerate(zip(distances[0], indices[0]), start=1):
        print(f"{rank}위 (거리 {dist:.3f}): {docs[idx]}")
```

IndexFlatL2는 정확한 탐색이라 문서가 적을 때 쓰기 좋고, 문서가 많아지면 IndexIVFFlat이나 IndexHNSWFlat 같은 ANN 인덱스로 바꾼다. FAISS는 벡터만 저장하므로 원본 텍스트와 메타데이터는 별도로 관리해야 한다는 점이 Chroma와의 차이다.

### 운영 관점의 고려사항

벡터 DB를 실제 서비스에 올릴 때는 개발 단계와 다른 고민이 생긴다. 첫째, 백업이다. 임베딩을 다시 만드는 데 시간과 비용이 들므로, 벡터 DB의 데이터를 정기적으로 백업한다. 원본 문서와 청킹 설정만 있어도 복원은 가능하지만, 시간이 오래 걸린다.

둘째, 재인덱싱 계획이다. 임베딩 모델을 바꾸거나 청킹 전략을 바꾸면 전체 문서를 다시 인덱싱해야 한다. 문서가 많을수록 이 작업이 오래 걸리므로, 새 인덱스를 별도로 만들고 검증한 뒤 전환하는 방식을 쓴다. 서비스 중단 없이 바꾸는 것이 목표다.

셋째, 모니터링이다. 검색 응답 시간과 검색 결과의 품질을 주기적으로 확인한다. 문서가 계속 늘어나면 인덱스 크기가 커지고 응답 시간이 느려질 수 있다. 임계값을 정해 두고 넘으면 알림을 받도록 한다.

### 핵심 정리

- 벡터 데이터베이스는 벡터와 원본 문서를 함께 저장하고 질문과 가장 가까운 벡터를 빠르게 찾아주는 전용 저장소다.
- 대규모에서는 모든 벡터와 거리를 재는 것이 불가능하므로 ANN 같은 근사 탐색으로 속도와 정확도를 맞바꾼다.
- Chroma와 FAISS는 프로토타입에, pgvector는 기존 PostgreSQL 환경에, Qdrant·Milvus는 대규모 서버 운영에, Pinecone은 관리형이 필요할 때 적합하다.
- Chroma는 설치가 간단해 실습과 소규모 서비스의 출발점으로 좋으며, 메타데이터 필터로 검색 범위를 좁힐 수 있다.
