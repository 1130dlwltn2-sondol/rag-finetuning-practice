## 22. 리랭킹

하이브리드 검색으로 후보를 넓게 확보했다. 이제 그 후보 중에서 정말로 질문에 답하는 데 필요한 문서를 위로 올리는 작업이 남았다. 벡터 검색과 BM25는 각각 문서를 독립적으로 점수화하는 방식이라, 질문과 문서 사이의 미묘한 관련성을 판단하는 데 한계가 있다. 리랭킹은 이 간극을 메우는 정밀도 향상 단계다.

### 크로스엔코더의 원리

임베딩 기반 검색(바이엔코더)은 질문과 문서를 각각 별도로 벡터로 만든 뒤 유사도를 계산한다. 질문을 인코딩할 때 문서 내용을 전혀 보지 못하므로, 두 텍스트 사이의 상호작용을 포착할 수 없다. 예를 들어 "환불이 안 되는 경우는?"이라는 질문에 "환불이 가능한 경우는 다음과 같다"로 시작하는 문서는 단어 구성이 비슷해 높은 점수를 받을 수 있지만, 실제로는 질문과 정반대 내용을 담고 있다.

크로스엔코더(cross-encoder)는 질문과 문서를 하나의 입력으로 이어 붙여 모델에 함께 넣는다. "[질문] 환불이 안 되는 경우는? [문서] 환불이 가능한 경우는 다음과 같다"처럼 말이다. 모델 내부의 어텐션이 질문 토큰과 문서 토큰 사이를 직접 오가며 관련성을 판단하므로, 부정 표현이나 조건절 같은 미묘한 차이를 구분한다. 대가로 속도가 느리다. 문서마다 모델을 한 번씩 실행해야 하므로 전체 문서 집합에 적용할 수는 없고, 앞 단계에서 추린 수십 개 후보에만 적용한다. 전형적인 파이프라인은 "하이브리드 검색으로 상위 50개 확보, 리랭커로 상위 5개 선정"이다.

리랭커 모델로는 BGE reranker 시리즈가 널리 쓰인다. 다국어 버전(bge-reranker-v2-m3)은 한국어를 포함한 다국어를 지원하므로 한국어 서비스에 바로 적용할 수 있다. Cohere의 Rerank API처럼 API 형태로 제공하는 서비스도 있어, GPU 인프라 없이 시작할 수 있다.

### 언제 리랭킹을 추가하는가

리랭킹은 검색 파이프라인에서 가장 비용이 많이 드는 단계 중 하나다. 무조건 추가하는 것이 아니라, 측정을 통해 판단한다. 23장에서 다룰 평가 방법을 이용해 현재 검색의 정밀도를 측정하고, 병목이 "관련 문서를 못 가져오는 것"(재현율 문제)인지 "가져온 문서 중 관련 없는 것이 섞이는 것"(정밀도 문제)인지 구분한다. 정밀도가 병목으로 확인될 때 리랭킹을 추가한다. 재현율이 문제인데 리랭킹을 붙이면 후보 자체가 없으므로 효과가 없다. 이 경우 청킹이나 하이브리드 검색 쪽을 먼저 손봐야 한다.

또한 리랭킹은 지연 시간에 직접 영향을 준다. 크로스엔코더 50개 문서 추론은 GPU 환경에서도 수백 밀리초가 걸릴 수 있다. 실시간 응답이 중요한 서비스라면 후보 수를 50개에서 20개로 줄이는 식으로 타협점을 찾거나, 경량 리랭커를 사용한다.

### 따라 하기: BGE reranker로 후보 재정렬

```python
# pip install sentence-transformers
from sentence_transformers import CrossEncoder

# 1차 검색(하이브리드 등)에서 확보한 상위 후보라고 가정
query = "약정 기간 중 해지하면 위약금이 얼마야?"
candidates = [
    "약정 기간 내 해지 시 잔여 개월 수에 비례하여 위약금이 부과된다.",
    "요금제 변경은 고객센터 앱 또는 홈페이지에서 신청할 수 있다.",
    "위약금은 최대 30만원을 초과하지 않으며, 잔여 개월에 따라 계산된다.",
    "휴대폰을 분실한 경우 분실 신고 후 일시 정지를 신청할 수 있다.",
    "약정 할인을 받은 고객은 약정 기간을 채우는 것이 유리하다.",
]

# BGE 다국어 리랭커 로드 (한국어 지원)
reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

# 질문-문서 쌍을 만들어 관련성 점수 계산
pairs = [[query, doc] for doc in candidates]
scores = reranker.predict(pairs)

# 점수 내림차순으로 재정렬하여 상위 3개 선택
ranked = sorted(zip(candidates, scores), key=lambda x: -x[1])
print("질의:", query)
for doc, score in ranked[:3]:
    print(f"점수 {score:.3f} | {doc}")
```

위 예제에서 1차 검색 순위가 어떻든, 리랭커는 "위약금 부과"와 "최대 30만원"을 직접 언급한 문서를 위로 올린다. 단어 빈도만으로는 구분하기 어려운 "약정 할인이 유리하다" 같은 주변 문서는 아래로 내려간다.

실전에서는 리랭커 입력 전에 후보를 한 번 더 다듬는 것이 좋다. 중복 문서를 제거하고, 너무 짧거나 광고성 문구 위주의 문서를 필터링하면 리랭커의 연산 낭비를 줄일 수 있다. 또한 리랭커 점수 자체를 임계값으로 잘라내는 방법도 있다. 점수가 일정 기준 이하인 문서는 LLM에 전달하지 않음으로써, 관련 없는 컨텍스트로 인한 환각을 줄인다.

### 바이엔코더와 크로스엔코더의 차이

두 구조의 차이를 정리하면 다음과 같다.

| 구분 | 바이엔코더 (임베딩 검색) | 크로스엔코더 (리랭킹) |
|---|---|---|
| 입력 | 질문과 문서를 각각 인코딩 | 질문과 문서를 이어 붙여 함께 입력 |
| 상호작용 | 없음 (유사도는 사후 계산) | 어텐션으로 토큰 간 직접 상호작용 |
| 속도 | 빠름 (벡터는 미리 계산) | 느림 (문서마다 추론 필요) |
| 용도 | 전체 문서에서 후보 추출 | 후보 수십 개의 순서 정밀 조정 |

이 표에서 알 수 있듯 둘은 경쟁 관계가 아니라 역할 분담 관계다. 바이엔코더가 넓게 걷어오고 크로스엔코더가 정밀하게 고른다.

### API형 리랭커 사용하기

GPU가 없거나 빠르게 시작하고 싶다면 API형 리랭커를 쓴다. Cohere Rerank가 대표적이다. 사용법은 간단하다. 질문과 문서 목록을 보내면 관련성 순으로 정렬된 결과를 돌려준다.

```python
# pip install cohere
import cohere

co = cohere.Client("COHERE_API_KEY")  # 실제 키로 교체 (코드에 키를 직접 넣지 말고 환경변수 사용)

query = "약정 기간 중 해지하면 위약금이 얼마야?"
documents = [
    "약정 기간 내 해지 시 잔여 개월 수에 비례하여 위약금이 부과된다.",
    "요금제 변경은 고객센터 앱 또는 홈페이지에서 신청할 수 있다.",
    "위약금은 최대 30만원을 초과하지 않으며, 잔여 개월에 따라 계산된다.",
]

response = co.rerank(
    model="rerank-multilingual-v3.0",  # 다국어 모델
    query=query,
    documents=documents,
    top_n=2,  # 상위 2개만 반환
)
for r in response.results:
    print(f"점수 {r.relevance_score:.3f} | {documents[r.index]}")
```

API형은 호출당 비용이 들지만 인프라 관리가 필요 없다. 트래픽이 적거나 검증 단계에서는 API형으로 시작하고, 트래픽이 늘면 자체 호스팅으로 전환하는 것이 일반적이다.

### 점수 임계값으로 관련 없는 문서 걸러내기

리랭커 점수는 순위뿐 아니라 필터로도 쓸 수 있다. 상위 5개를 무조건 LLM에 전달하는 대신, 점수가 일정 기준 이하인 문서는 제외한다. 이렇게 하면 관련 없는 컨텍스트가 프롬프트에 들어가는 것을 막아 환각을 줄인다.

```python
# 리랭커 점수 임계값 필터링 (앞 예제의 ranked를 이어서 사용)
THRESHOLD = 0.0  # bge-reranker-v2-m3 점수 기준, 데이터에 맞게 조정
filtered = [(doc, s) for doc, s in ranked if float(s) >= THRESHOLD]

if not filtered:
    # 관련 문서가 하나도 없으면 "모르겠다"고 답하는 편이 낫다
    print("관련 문서를 찾지 못했습니다. 검색 범위를 넓히거나 질문을 바꿔보세요.")
else:
    print(f"{len(filtered)}개 문서를 LLM에 전달합니다.")
```

임계값은 데이터마다 다르므로 테스트셋으로 조정한다. 너무 높이면 정답 문서를 놓치고, 너무 낮으면 필터 의미가 없다. 23장의 context_precision과 함께 보면 적절한 지점을 찾기 쉽다.

### 리랭킹 도입 체크리스트

리랭킹을 붙이기 전에 다음을 확인한다.

- 정밀도가 병목인가: context_precision이 낮고 context_recall은 괜찮은가.
- 지연 시간 예산이 있는가: 후보 50개 기준 리랭커 추론 시간을 측정했는가.
- 폴백이 있는가: 리랭커 장애 시 1차 검색 결과 그대로 답변할 수 있는가.

리랭커는 외부 의존성이므로 장애 대응이 필요하다. API형이라면 타임아웃과 재시도 정책을 두고, 자체 호스팅이라면 모델 로딩 실패 시 우회 경로를 둔다. 검색 품질만큼 운영 안정성도 중요하다.

### 자체 호스팅과 API형의 선택 기준

| 구분 | 자체 호스팅 (BGE 등) | API형 (Cohere Rerank 등) |
|---|---|---|
| 초기 비용 | GPU 인프라 필요 | 없음, 호출당 과금 |
| 지연 시간 | 인프라에 따라 조절 가능 | 네트워크 왕복 추가 |
| 데이터 보안 | 문서가 외부로 나가지 않음 | 문서 내용이 외부 전송됨 |
| 잘 맞는 경우 | 트래픽이 많고 꾸준함 | 검증 단계, 트래픽이 적음 |

보안 요구사항이 있는 사내 문서 서비스라면 자체 호스팅이 사실상 필수다. 문서 내용을 외부 API에 보낼 수 없기 때문이다. 반대로 빠르게 검증하고 싶은 프로토타입이라면 API형으로 시작하는 것이 합리적이다.

### 배치 추론으로 지연 시간 줄이기

크로스엔코더는 문서마다 한 번씩 추론하므로 후보가 많을수록 느리다. 속도를 올리는 가장 쉬운 방법은 배치 추론이다. 질문-문서 쌍을 하나씩이 아니라 묶어서 모델에 넣으면 GPU 활용률이 올라간다. sentence-transformers의 CrossEncoder.predict는 내부적으로 배치를 처리하므로, 위 예제처럼 리스트를 통째로 넘기는 것만으로도 배치 효과가 난다. 배치 크기는 GPU 메모리에 맞게 조정한다. 너무 크면 메모리 부족으로 실패하므로 16이나 32부터 시작해 늘려본다.

또한 캐싱을 고려한다. 같은 질문이 반복되는 서비스라면 리랭킹 결과를 일정 시간 캐시한다. FAQ성 질문이 많은 사내 챗봇에서는 캐시 적중률이 높아 지연 시간과 비용을 동시에 줄일 수 있다.

### 도메인 적응: 리랭커 파인튜닝

공개 리랭커가 특정 도메인에서 잘 안 맞는다면 파인튜닝을 고려한다. 크로스엔코더 파인튜닝에는 질문, 긍정 문서, 부정 문서의 트리플이 필요하다. 긍정 문서는 질문에 답하는 문서, 부정 문서는 비슷해 보이지만 답이 안 되는 문서다. 부정 문서를 잘 고르는 것이 핵심이다. 무작위 문서가 아니라 1차 검색에서 상위에 올랐지만 실제로는 관련 없는 문서를 부정 예시로 쓰면(hard negative), 모델이 미묘한 차이를 배운다.

데이터는 수백 개만 있어도 효과를 볼 수 있다. 서비스 로그에서 사용자가 "도움이 안 됐어요"라고 표시한 검색 결과를 부정 예시로 활용하면 자연스럽게 학습 데이터가 쌓인다. 파인튜닝한 리랭커는 주기적으로 재평가해 성능이 유지되는지 확인한다.

### 핵심 정리

- 크로스엔코더는 질문과 문서를 함께 입력해 관련성을 직접 판단하므로, 바이엔코더보다 정밀한 순위 매기기가 가능하다.
- 전형적인 파이프라인은 1차 검색으로 상위 50개 확보 후 리랭킹으로 상위 5개를 선정하는 구조다.
- 리랭킹은 정밀도가 측정된 병목일 때만 추가한다. 재현율 문제에는 효과가 없다.
- 지연 시간과 비용을 고려해 후보 수와 모델 크기를 조정하고, 리랭커 점수 임계값으로 관련 없는 문서를 걸러낸다.
